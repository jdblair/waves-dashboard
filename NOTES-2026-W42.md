# Notes 2026-W42

## 2026-10-16 — origin

`wave` and waves-dashboard were first built inside another project and
moved here once they proved useful on their own. The two sections below
carry over that project's design notes for them, with paths updated for
this repo's layout.

### waves-dashboard design

The rationale behind the less obvious decisions:

- **bd kv for wave facts, not an epic per wave.** An epic would duplicate the
  `wave-N` label, and every timestamp written to it bumps `updated_at`,
  which is exactly why labels are never backfilled onto old beads. kv syncs
  with Dolt and touches no bead.
- **A label marks membership, not dispatch.** Waves are often labelled while
  still planned (`wave-8` … `wave-11` sitting queued), so a label's existence
  says nothing about when a wave started. Dispatch time has to be recorded
  on its own.
- **Wave names aren't always numbers** (a one-issue wave can be named after
  the issue's short id), so kv keys use the label suffix:
  `wave.<name>.dispatched`.
- **The vui + beads private helpers risk was accepted** for the identical
  look and the small amount of code. A load-time smoke test is the guard.
- **Deploy facts often exist informally** in close reasons such as
  `Deployed 2026-10-16 (trunk <sha>; …)`. That is the fallback for waves
  with no kv record.

### Found by running it (2026-10-16)

Four things found by running `bin/wave` and `waves-dashboard.el` against a
real ~740-bead project, not by reading code:

- **bd 1.2.2 ignores `--label-pattern` and `--label-regex`.** Both return
  every bead, so the filters are silently dropped.
- **`bd label list-all` took 22 s** while `bd list --all --json` took 0.4 s
  (on a loaded machine, but the ratio is the point). The loader does one
  `bd list --all` and filters in Elisp.
- **Concurrent bd processes in one project stall** on embedded Dolt's
  exclusive `noms/LOCK`. Parallel loaders sat at "Loading…" forever, so bd
  calls now run in sequence.
- **Not every merge into trunk is a wave merge.** A merge whose subject only
  *mentioned* a wave's bead stretched that wave back eight days and gave it
  143 "opened" beads. Only ids in a `Merge <ids>:` prefix count.

Backfilling kv facts for waves that ran before `wave` existed works, but
only for facts with a source: deploy times from close reasons, titles from
the notes. Dispatch times with no record were left out rather than guessed.

### Packaging decision

- **waves is its own project**: the bead-waves skill, bin/wave and
  waves-dashboard.el together, depending on beads (bd and beads.el) and vui.
  It is useful without anything else built around it.

## 2026-10-16 — repo created

- **Plain copy, not a history-preserving split.** All of it came from one
  commit in the original project, so a filter-repo split would carry one
  commit and unrelated paths in its message.
- **Layout**: `waves-dashboard.el` at the root so `use-package :vc` and
  `package-vc-install` find the main file without `:lisp-dir`; tests and
  fixtures in `test/`; the skill in `skill/bead-waves/` so it can be
  symlinked into `~/.claude/skills/` as a directory.
- **Package-Requires**: `(emacs "29.1") (vui "1.0.0") (beads "0.1.0")`.
  Those are what beads.el's own header declares (it requires vui 1.0.0 and
  is itself 0.1.0); waves uses nothing newer than beads.el does.
- **`-L` per `~/.emacs.d/elpa/*/` does not reach beads.el**, whose sources
  are in `elpa/beads/lisp/`; it fails with "Cannot open load file …
  beads-section". The Makefile adds that dir.
- **`use-package :vc` with a local `:url "~/…"` fails** ("Empty
  checkout"); it needs an absolute path. With one, it installs and the
  autoload works (tried in a throwaway `package-user-dir`).

## 2026-10-16 — synthetic fixtures

- **The test fixtures are synthetic**: an invented static-site generator
  project with `demo-` ids. They keep the shape of the real snapshot the
  tests were first written against (waves 6, 7, 8–11 and a non-numeric
  `hotfix`; deploys only in close reasons; merges in the `Merge <ids>: text`
  form plus a non-bead `Merge cssfix: …`; a wave-7 bead created inside
  wave 6's window), so every test still exercises the same case.
- **Two cases were added**, because a mutation check showed the snapshot
  didn't exercise them: a wave-6 bead closed after the deploy with a
  non-`Deployed` reason (without it, a fallback that ignores close reasons
  still passed), and a full bead id after the colon of the `cssfix` merge
  (without it, counting ids after the colon still passed the merges test).

## 2026-10-16 — wrapping, re-queued beads, folding

- **Wrapping uses `wrap-prefix`, not re-rendering.** Each line carries
  `(space :align-to COL)`, so the display re-wraps on resize. The issue-row
  title column mirrors beads' own format string
  (`waves-dashboard--issue-head`), and a test checks it against a rendered
  row. If beads changes that format, the test fails.
- **Dim rows are built alongside beads' row**, not by passing a face to it.
  `beads-section--plain-button` forces `beads-issue-line`, which overrides any
  face in EXTRA-PROPS (checked).
- **"Re-queued" never changes a wave's state.** The owner decided to keep the
  state rules. It's a marker, a default fold and a header note. "Later"
  means a later start, with unstarted waves last and ties by name.
- **Subsection fold state shares the `:collapsed` alist**, keyed
  `<wave>/<part>`. The defaults: folded when everything in the part is
  closed, and merges follow the wave's beads.
- **The Makefile puts `-L .` first and filters out an installed
  waves-dashboard.** Emacs keeps `-L` order, and the first match wins. Before
  this, `make test` exercised the VC-installed copy.
- **Install order:** package.el only fetches dependencies from archives, so
  beads.el (on no archive) needs its own `:vc` block before this one. Both
  orders were checked on a fresh `package-user-dir`.

## 2026-10-16 — per-bead model selection (design, not implemented)

- **The coordinator picks a model per bead** when it spawns the agent
  (the Agent tool's `model` override). One agent per bead, as now; no
  splitting a bead across models.
- **Criteria, kept simple.** Default to the cheaper model (sonnet) for a
  bead that is small and well specified: a clear fix, a rename, docs, a
  test for existing behaviour, a one-file change. Use the stronger model
  for anything that needs design judgment, touches several files or
  modules, or has a vague description. When in doubt, use the stronger one.
- **An explicit label overrides the guess.** A bead labelled `model:strong`
  or `model:cheap` is spawned that way.
- **Escalate on failure.** If a cheap-model bead fails review or its tests,
  re-queue it on the stronger model. The dashboard already marks re-queued
  beads.
- **The code review stays on the stronger model.** A cheap model's mistakes
  are only caught if the reviewer is not also cheap.
- **Risk:** a cheap model can produce plausible but wrong work that passes
  a shallow review. Record which model handled each bead and whether it
  was retried, so the heuristic can be tuned from real results.
- **The model is recorded in bd kv**, `wave.<name>.model.<id>`, set with
  `wave model <name> <id> <model>`. Like the other wave facts, this bumps
  no bead's `updated_at`. It is per wave, so a retry in a later wave shows
  its own model. The dashboard prints `[model]` after the bead's row.
